Control framework

Compliance is not a gateway at the end

The control model lives alongside the process. It constrains actions, creates work, drives communications and preserves evidence of why the organisation acted.

Control register

Controls are classified so the publication does not turn a design preference into a legal claim. “CODE” means an industry Code standard relevant to Code subscribers and scope. “PRUDENTIAL” means an APRA requirement relevant to APRA-regulated entities. “DESIGN” is this architecture’s control choice.

Control philosophy

Controls can be action-specific

A payment control can block payment without preventing a customer update or evidence-gathering action.

Controls should create data

A block should produce a reason, source, timestamp, owner and next possible path, not just an opaque exception.

Controls can be continuous

Timers, complaint recognition, vulnerability support, supplier performance and investigation scope should be monitored while the claim is moving.

Controls need an exception model

Where an obligation or internal policy permits an alternative timetable or authorised exception, the reason and authority should be explicit.
